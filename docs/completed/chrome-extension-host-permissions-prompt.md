Context: `manifest.json` requested `host_permissions: ["https://*/*", "http://*/*"]` plus a `"tabs"` permission and a static `content_scripts` entry injecting `content.js` into every page on `document_idle`, matching all URLs. The extension's own original requirements doc (`future-signals-chrome-extension-requirements.md`, section 21) explicitly flagged this and told the developer to evaluate narrowing to `activeTab` before shipping: "for Chrome Web Store review and user trust, be conservative... evaluate whether broad host permissions are necessary." That evaluation had never been done. Broad `host_permissions` also trigger Chrome Web Store manual review and require a written per-permission justification in the submission form, and show a scarier install-time permission prompt to users ("Read and change all your data on all websites").

The fix has already been implemented (not by you), three files:
- `extension/public/manifest.json` — removed `host_permissions` entirely, removed the static `content_scripts` block, removed the standalone `"tabs"` permission (every `chrome.tabs.*` call in the codebase only ever targets the single active tab — `chrome.tabs.query({active:true,...})`, `chrome.tabs.sendMessage`, `chrome.tabs.get` on that one tab id — which `activeTab` already covers once granted), and added `"scripting"` to permissions (required for `chrome.scripting.executeScript`). `permissions` is now `["storage", "sidePanel", "activeTab", "scripting"]` and there's no `host_permissions` key at all.
- `extension/src/lib/activeTabPage.ts` — added `ensureContentScriptInjected(tabId)`, called at the top of `fetchActiveTabPage()` before the existing `chrome.tabs.sendMessage` call. It best-effort injects `content.js` via `chrome.scripting.executeScript({ target: { tabId }, files: ["content.js"] })`, swallowing errors (pages Chrome won't allow injection into — `chrome://`, the Web Store, etc. — fall through to the existing `chrome.tabs.get`-only fallback exactly as before). `activeTab` grants this permission because opening the side panel (via the toolbar icon) is itself the user-invocation that activates it for the current tab.
- `extension/src/content.ts` — wrapped the entire file body (both the `FS_GET_PAGE_DATA` message listener and the `selectionchange` watcher) in a `window.__fsContentScriptLoaded` guard. This is now required because injection is on-demand rather than a single guaranteed manifest-driven injection per page load: `fetchActiveTabPage()` re-injects on every call (side panel mount, "Reload from active tab", etc.), and without the guard a second injection into a page that already has the script would double-register both listeners — duplicate message responses, duplicate `FS_SELECTION_CHANGED` pushes on every selection.

**One real, deliberate behavior change worth testing for and being aware of:** with the old always-on `content_scripts`, the script was present on every page from load, before the user ever opened the extension. With `activeTab`-only injection, the script only gets added to a tab at the moment `fetchActiveTabPage()` runs (panel opening, or clicking "Reload from active tab"). Practical effect: if the side panel is already open and the user navigates to a *new* page in that same tab, the automatic "selection pushes to the Description field without clicking Reload" feature won't reactivate on that new page until the user manually clicks "Reload from active tab" once (which re-triggers injection). This is a minor, expected cost of the narrower permission model, not a bug — flag it back only if it feels worse in practice than it sounds on paper.

`npx tsc --noEmit` was run in a sandboxed environment and shows no new errors beyond the same pre-existing warnings from every prior pass.
