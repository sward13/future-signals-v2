Context: the extension's password reset was broken end to end. `AuthView.tsx` only had `"signin" | "signup" | "forgot"` modes — no `"reset"` mode existed to actually set a new password. `handleForgot` sent the recovery email with `redirectTo: chrome-extension://<id>/sidepanel.html`, but `createExtensionSupabase()` set `detectSessionInUrl: false`, so even when that link opened the side panel with a `#access_token=...&type=recovery` fragment, the Supabase client was explicitly configured to ignore it — `getSession()` would just return null.

The fix mirrors the main app's proven pattern exactly (`src/App.jsx` + `src/components/auth/AuthScreen.jsx`), rather than inventing a new mechanism:

The fix has already been implemented (not by you), three files:
- `extension/src/lib/createSupabase.ts` — `detectSessionInUrl: false` → `true`. This is what makes the Supabase client actually parse the recovery token out of the URL when the side panel opens via the reset-link redirect. It's a no-op on every other panel-open path (toolbar click has no URL params to detect).
- `extension/src/sidepanel/App.tsx` — added a `passwordRecovery` boolean state. The `onAuthStateChange` listener now special-cases two events: `PASSWORD_RECOVERY` sets `passwordRecovery = true` (and still updates `session`), `USER_UPDATED` sets `passwordRecovery = false`. A new render gate — `if (passwordRecovery) return <AuthView supabase={supabase} initialMode="reset" />` — sits *before* the `if (!session)` check, exactly matching `App.jsx`'s `if (passwordRecovery) return <AuthScreen initialMode="reset" />` ordering. This matters: Supabase's recovery flow establishes a real (if temporary) session, so without this gate ordered first, a recovery session would fall through into the normal signed-in capture form instead of forcing a "choose a new password" screen.
- `extension/src/sidepanel/AuthView.tsx` — added `initialMode` prop (defaults to `"signin"`), extended the mode union to include `"reset"`, added a `confirmPassword` field, and added `handleReset`: validates `password === confirmPassword`, validates a 6-character minimum, calls `supabase.auth.updateUser({ password })`, and on success resets the password fields and switches back to `"signin"` mode (session is already valid at that point from the recovery flow, and `USER_UPDATED` will have already flipped `passwordRecovery` false at the `App.tsx` level, so the app proceeds into the normal capture flow — the `setMode("signin")` call is mostly for the moment before that state propagates). The sign-in/sign-up mode tabs are now hidden while in `"forgot"` or `"reset"` mode (previously they stayed visible even during forgot, which was a pre-existing minor inconsistency with the main app, fixed as a drive-by).

One intentional simplification versus the main app: the extension's reset form uses plain `type="password"` inputs with no show/hide eye-icon toggle (main app's `AuthScreen.jsx` uses `lucide-react`'s `Eye`/`EyeOff`). `lucide-react` isn't a dependency of `extension/package.json` and this pass didn't add one — flag it back if you think the toggle is worth the new dependency, otherwise leave as is.
