Audit: Chrome Extension vs. Main App Alignment (Auth, Input Creation, Security)

Scope: `extension/` compared against `src/`, `schema.sql`, `CLAUDE.md`, and `future-signals-chrome-extension-requirements.md`. Read-only diagnostic. No code changed.

## 1. Auth

**Resolved (commit `1a78b5f`).** `AuthView.tsx` now has a fourth `"reset"` mode with a full reset-password form (match + 6-character-minimum validation), `createSupabase.ts`'s `detectSessionInUrl` is now `true`, and `App.tsx` gates on `PASSWORD_RECOVERY`/`USER_UPDATED` auth events exactly like the main app's `App.jsx`/`AuthScreen.jsx`. Two additional issues surfaced only by testing against a live reset email, both fixed in the same commit: (1) `manifest.json` had no `web_accessible_resources` entry, so Chrome blocked the reset-email link outright (`ERR_BLOCKED_BY_CLIENT`) before any of the auth code could run — clicking a `chrome-extension://` link from an external page (e.g. an email client) requires the target page to be explicitly listed there; (2) since the reset link now opens `sidepanel.html` as a full, undocked browser tab rather than the ~400px docked panel, the layout had no max-width and stretched full-bleed — `sidepanel.html` now caps and centers `#root` at 420px. Manually tested end to end against a live reset email in both staging and production Supabase projects (redirect URL allowlisted in both), including the mismatched-password and under-6-character validation paths and signing back in with the new password.

**Two fully independent auth surfaces, by design, but drifted.** CLAUDE.md states "Chrome extension is a separate surface, handled independently," so a second sign-in UI is a confirmed, intentional decision, not an oversight. But the two implementations have diverged in small ways worth reconciling: the main app shows a password visibility toggle (Eye/EyeOff) on every password field and enforces a 6-character minimum in its reset form; the extension's `AuthView.tsx` has neither a visibility toggle nor any password-length validation. The main app also renders a dedicated "Check your email" confirmation screen gated on its own `signupConfirmed` boolean, deliberately decoupled from `mode` so it survives auth-state-change events; the extension instead shows an inline `info` banner in the same form, which is a thinner version of the same idea.

**Session storage is intentionally separate.** The extension persists its Supabase session in `chrome.storage.local` via a custom `chromeLocalAuthStorage` adapter; the main app uses its own client at `src/lib/supabase.js` (default browser storage). A user must sign in to each surface independently. The original `future-signals-chrome-extension-requirements.md` (section 12) proposed a session handoff from the web app instead, specifically to avoid a second sign-in. That recommendation was not the path taken. Worth flagging only to confirm this was a deliberate trade, since it's the biggest deviation from the original auth spec.

**Workspace lookup is correct, but the failure path is a dead end.** `fetchWorkspaceIdForUser()` assumes one workspace per user via `.maybeSingle()`. That matches the schema (`workspaces.user_id` is unique, created by a signup trigger, 1:1 with `auth.users` in v2), so this part is aligned. If a user opens the extension in the brief window between `signUp()` and the workspace-creation trigger completing, `App.jsx` shows "No workspace found for this account" with only a sign-out button, no retry or wait-and-recheck. Worth a manual test of that timing window before publishing.

## 2. Creating and saving inputs

**Resolved (commit `1d5749f`).** The extension previously wrote `signal_quality: null` on every insert, a column CLAUDE.md confirms is "retained but unused" after Signal Quality was disaggregated into Signal Strength (Weak | Moderate | Strong) and Source Confidence (Low | Medium | High). Every display and filter surface in the main app (`Inbox.jsx`, `ClusterScreen.jsx`, `Clustering.jsx`, `ProjectDetail.jsx`, `InputDetailDrawer.jsx`, `ExportModal.jsx`) reads `signal_strength` and `source_confidence`, never `signal_quality`. The capture form now includes both fields (same ids and labels as `InputDrawer.jsx`: weak/moderate/strong, low/medium/high), persists them in the draft, and writes to `signal_strength` / `source_confidence` on save. Built and manually verified in Chrome.

**STEEPLED category is still absent from the extension.** `InputDrawer.jsx` shows a `SteepleSelector` for the Signal, Issue, Plan, and Obstacle types, letting a practitioner tag one or more of the eight STEEPLED categories at creation time. The extension's capture form has no equivalent control, and `insertInputAndRequestEmbed()` always writes `steepled: []`. This was in scope for the original requirements doc's "Add details" expansion (section 6) and was never built. Worth a decision on whether it belongs in the extension now, following the same pattern used for Signal Strength / Source Confidence.

**Provenance tagging uses a key the rest of the app doesn't recognize.** The main app has an established convention for tagging where an input came from: `metadata.source` (e.g., `"scanner"` for AI-suggested/seeded inputs, checked throughout `AppShell.jsx`, `Dashboard.jsx`, `Inbox.jsx`, `ProjectOverview.jsx`, `ProjectDetail.jsx`, `InputDetailDrawer.jsx`). The extension instead writes `metadata.capture_source: "chrome_extension"`. If the product ever wants to badge or filter "captured via extension" inputs the same way it already badges scanner-sourced ones, today's extension-created rows won't match any existing `metadata?.source` check. This is a small, mechanical fix: either add `source: "chrome_extension"` alongside (or instead of) `capture_source`, or explicitly decide the two provenance concepts should stay separate.

**Required-field behavior is actually aligned.** Both surfaces enforce only Title/Name as required (`InputDrawer.jsx`'s `handleSave` checks `fields.title.trim()`; the extension's `submit()` checks `name.trim()`). No gap here.

**`embed-input` invocation pattern matches.** Both the extension and every main-app insert path (`useAppState.js`, `Clustering.jsx`, `ScannerInboxStep.jsx`) call `supabase.functions.invoke("embed-input", ...)` fire-and-forget with `.catch(() => {})`, silently swallowing failures so the user-facing save still succeeds. Confirmed aligned.

**Draft persistence has no main-app analogue.** The extension deliberately preserves an unsaved capture draft in `chrome.storage.local` across sign-out (README item 11, by design). The main app has no equivalent "draft survives sign-out" concept for input creation. This raises one edge case worth noting: a stale draft can reference a `project_id` for a project that's since been deleted or made inaccessible. `sanitizeSaveError()` does handle an RLS/permission-denied response, but the resulting message ("Permission denied. You may not have access to save here.") doesn't tell the user their saved project no longer exists, which could be confusing. Minor polish item.

**Long-selection truncation from the original spec was not implemented.** `future-signals-chrome-extension-requirements.md` (section 9) called for truncating selected text over 2,000 characters with a small note. Nothing in `CaptureForm.tsx` or `metadata.ts` truncates or warns; the full selection is passed through as-is. Low severity, but worth a decision either way.

## 3. Visual parity

Confirmed against screenshots of both surfaces side by side.

**Resolved.** `InputDrawer.jsx` renders Signal Strength / Source Confidence with `ThreeCardSelector` (`InputFormFields.jsx`): a 3-column grid of bordered cards, each with a colored dot, a title, a description line, and a checkmark on the selected card. The extension's original `ToggleOptionRow.tsx` was modeled on `HorizonSelector` instead — a flat, single-row segmented control — which caused the mismatch flagged during manual verification. The extension now has its own `ThreeCardSelector.tsx` mirroring the main app's card pattern (dot color by tier position: amber/blue/green), swapped into `CaptureForm.tsx` for these two fields. Built and manually verified in Chrome against side-by-side screenshots; no cramping or wrapping issues at the side panel's actual width. `ToggleOptionRow.tsx` is kept unused for now — it's the right pattern for Time Horizon, which the main app itself renders as a flat toggle, not a card.

**STEEPLED category and Time horizon are entirely absent from the extension's form**, not just styled differently. `InputDrawer.jsx` shows `SteepleSelector` (an 8-pill grid, "Select all that apply") and `HorizonSelector` (H1/H2/H3 toggle) for Signal-type inputs, in addition to Signal Strength / Source Confidence. The extension's capture form has no equivalent for either. STEEPLED was already noted above; Time horizon is a new gap surfaced by this pass — `insertInputAndRequestEmbed()` hardcodes `horizon: null`.

**The main app's form includes editorial scaffolding the extension's doesn't.** A colored type-description banner ("A concrete, observable piece of evidence — an event, data point, or article that points toward change.") sits below the type chip, and a "Type fields" section divider separates the common fields (Title/Description/Source URL) from the type-specific ones. The extension has neither — its type chip has no description banner beneath it, and there's no visual separation between the always-present fields and the classification fields.

**What's already aligned:** the type-switcher chip itself (rounded colored pill, icon + label + caret, same colors per type) matches closely between the two screenshots. The overall three-field base (Title/Description/Source URL) and the general `tokens.js` typography/spacing scale are shared correctly — the divergence is specific to the type-fields section, not the form as a whole.

Not yet decided: whether to rebuild `ToggleOptionRow` on `ThreeCardSelector`'s pattern (dot + description) to match exactly, or keep a condensed treatment intentionally suited to the side panel's ~360px width and just add the missing dot/description elements. Adding STEEPLED and Time horizon are separate scope decisions from the styling question.

## 4. Security

**Resolved (commit `4225c11`).** `host_permissions`, the standalone `"tabs"` permission, and the static `content_scripts` entry are gone. `permissions` is now `["storage", "sidePanel", "activeTab", "scripting"]`, and `content.js` is injected on demand via `chrome.scripting.executeScript` from `activeTabPage.ts`, right before messaging it — guarded against double-injection via a `window.__fsContentScriptLoaded` flag. Section 21 of `future-signals-chrome-extension-requirements.md` is now satisfied. Manually verified: install/reload no longer shows "Read and change all your data on all websites"; the core capture loop (title/URL/selection autopopulate, live selection push, Reload from active tab, save to Supabase) all still work; a page Chrome won't allow injection into (e.g. `chrome://extensions`) falls back gracefully to title/URL only, no crash.

Getting `activeTab` actually granted required two more fixes, neither anticipated going in, both found only by testing the built extension rather than by reading the diff: (1) `background.ts` opened the side panel via `chrome.sidePanel.setPanelBehavior({ openPanelOnActionClick: true })`, which Chrome's own docs state is incompatible with `activeTab` — that path bypasses `chrome.action.onClicked` entirely, and `activeTab` is only granted in response to that event actually firing, so nothing worked, not even on the very first page opened. Fixed by opening the panel from an explicit `onClicked` listener calling `chrome.sidePanel.open()` instead. (2) `openPanelOnActionClick` turned out to be a setting Chrome persists per-extension rather than something derived from whether the code calls it — an earlier build had called it with `true` on every load, so removing the call alone didn't undo it; had to explicitly call `setPanelBehavior({ openPanelOnActionClick: false })` to reset it. Both fixed in the same commit as the permission narrowing itself.

One deliberate, tested-and-accepted behavior change from the old always-on content script: if the side panel is already open on page A and the user navigates that same tab to page B, the automatic "selection pushes to Description without clicking Reload" feature doesn't reactivate on page B until "Reload from active tab" is clicked once (re-triggering injection). Confirmed as expected, not a bug, during manual verification.

**What the always-on content script actually does is worth stating explicitly for the record.** `content.ts` only responds to an explicit `FS_GET_PAGE_DATA` message (on-demand, side-panel-initiated) and pushes `selectionchange` events to the side panel over `chrome.runtime.sendMessage` (silently ignored if the panel isn't open). Nothing here reaches Supabase or any network endpoint except through the user-initiated Save action. The current code looks benign; the concern is exposure surface, meaning broad permissions and a script running on every page a user visits.

**RLS is clean and consistent, and the extension rides on it correctly.** `schema.sql`'s policies for `workspaces`, `projects`, `inputs`, `clusters`, and `cluster_inputs` are all scoped through the same `get_workspace_id()` helper (`select id from public.workspaces where user_id = auth.uid()`), and the extension's anon-key client goes through the same authenticated session, so it inherits the same scoping with no bypass found. This is aligned. One caveat: `schema.sql` itself is stale in at least one place (it still lists `signal_quality` without `signal_strength`/`source_confidence`, which the live `database.types.ts` and every component actually use). Treat `schema.sql` as a rough reference rather than ground truth for any further RLS/security review.

**Password-reset redirect allowlist.** The README correctly calls out that `chrome-extension://<YOUR_EXTENSION_ID>/sidepanel.html` needs to be added to Supabase's Auth redirect URL allowlist. Worth confirming this is actually configured in both the staging and production Supabase projects, separate from the broken client-side handling noted in section 1.

**No secret leakage found in the build.** `vite.config.ts` and `vite.content.config.ts` don't inject any custom `define` block; only Vite's standard `VITE_`-prefixed env vars are exposed, and the anon key is the only credential involved. No service-role key or other secret appears reachable from the bundled extension.
